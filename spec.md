Вот краткое и структурированное техническое задание (ТЗ) на разработку веб-приложения, основанное на вашем описании. Использование машины состояний (FSM) — это идеальный архитектурный подход для такой логики.

## Краткое техническое задание: Веб-приложение «Workaholism Monitor»

**Суть проекта:** Мобильное веб-приложение, которое с помощью фронтальной камеры и алгоритмов компьютерного зрения отслеживает присутствие пользователя перед экраном и принудительно контролирует режим работы и отдыха (25 минут работы / 5 минут отдыха).

---

### 1. Технический стек и интеграция CV

* **Платформа:** Web-приложение (PWA для возможности установки на смартфон/ПК и работы в фоне/с выключенным экраном, если поддерживается браузером).
* **Computer Vision:** `MediaPipe Face Landmarker` (Web JS API).
* **Конфигурация детекции:**
* Использование параметров `minFaceDetectionConfidence`, `minFacePresenceConfidence`, `minTrackingConfidence` для точной настройки чувствительности (чтобы повороты головы или плохое освещение не вызывали ложных срабатываний).
* Необходим механизм «debounce» (задержки): кратковременные потери лица (до 10 секунд) игнорируются таймером работы.



### 2. Пользовательский интерфейс (UI)

* **Основной экран:** Крупный минималистичный таймер текущей сессии (работа или отдых).
* **Цветовая индикация (Работа):**
* 0–20 минут: черный фон.
* 20–25 минут: плавная интерполяция фона от черного к красному.
* 25+ минут: полностью красный фон.


* **Экран отдыха:** Смена интерфейса на текстовое сообщение (например, «Отойдите от экрана, пора отдохнуть») и вывод таймера отдыха.
* **Режим отладки (Debug Mode):** Скрытый по умолчанию блок (`<video>` + `<canvas>`), который отображает видеопоток с камеры и отрисованные точки лица (landmarks). Включается по клику на невидимую зону или через параметр в URL.

---

### 3. Машина состояний (FSM)

Для реализации логики потребуется 6 основных состояний.

| Текущее состояние | Триггер / Условие | Выполняемое действие | Переход в состояние |
| --- | --- | --- | --- |
| **`IDLE`** (Ожидание) | Камера видит лицо пользователя. | Запуск таймера работы. Фон черный. | ➔ **`WORK`** |
| **`WORK`** (Работа) | Время сессии достигло 20 минут. | Фон начинает плавно краснеть. | ➔ **`WORK`** (смена UI) |
|  | Время сессии достигло 25 минут. | Фон красный. Одиночный звуковой сигнал. | ➔ **`OVERTIME`** |
|  | Лицо пропало на время **> 10 секунд**. | Таймер сессии ставится на паузу. | ➔ **`WORK_PAUSED`** |
| **`WORK_PAUSED`** (Пауза в работе) | Лицо вернулось в кадр. | Таймер работы возобновляется. | ➔ **`WORK`** или **`OVERTIME`** |
|  | Лицо отсутствует **> 5 минут**. | Сброс сессии (пользователь отдохнул сам). | ➔ **`IDLE`** |
| **`OVERTIME`** (Переработка) | Пользователь не уходит (лицо в кадре). | Таймер растет. Звуковой сигнал **раз в 1 минуту**. | Остается в **`OVERTIME`** |
|  | Лицо пропало (пользователь ушел). | Включается экран отдыха. Запуск таймера (5 мин). | ➔ **`REST`** |
| **`REST`** (Отдых) | Лицо вернулось в кадр (раньше времени). | Таймер отдыха на паузе. | ➔ **`REST_VIOLATION`** |
|  | Таймер отдыха достиг 5 минут. | Таймер останавливается. Ожидание пользователя. | ➔ **`IDLE`** |
| **`REST_VIOLATION`** (Нарушение отдыха) | Лицо находится в кадре. | Звуковой сигнал **раз в 1 минуту** (прогоняем). | Остается в **`REST_VIOLATION`** |
|  | Лицо пропало. | Таймер отдыха возобновляется. | ➔ **`REST`** |

### 4. Ключевые системные требования и нюансы

1. **Разрешения (Permissions):** При первом старте приложение должно запрашивать доступ к камере (`navigator.mediaDevices.getUserMedia`). Обязательна обработка отказа в доступе (показ инструкции).
2. **Аудио-контекст:** В современных браузерах звук не может воспроизводиться без первого взаимодействия пользователя со страницей (User Gesture Policy). Перед стартом мониторинга должна быть кнопка «Начать работу», клик по которой разблокирует AudioContext для последующих алертов.
3. **Энергопотребление:** Постоянная работа фронтальной камеры и MediaPipe сильно расходует батарею смартфона. Следует ограничить FPS для обработки CV (например, проверять кадр 2–5 раз в секунду, а не 30/60).
4. **Видимость страницы:** Рекомендуется использовать `Page Visibility API`, чтобы понимать, свернул ли пользователь браузер, и опционально отправлять ему системные Web Push уведомления, если он переключился на другую вкладку/приложение, но камера все еще захватывает его лицо.


### 5. Система аналитики и сбора статистики

#### 5.1. Логика записи (Хуки FSM)

При каждом значимом переходе машина состояний должна формировать объект события и сохранять его.
Например:

* Переход **`WORK` ➔ `OVERTIME**`: записываем успешную сессию работы (ровно 25 минут).
* Переход **`OVERTIME` ➔ `REST**`: записываем, сколько длилась переработка (разница между началом овертайма и уходом от экрана).
* Переход **`WORK_PAUSED` ➔ `IDLE**` (отсутствовал больше 5 минут): записываем фактическое время работы до ухода (например, 14 минут).

#### 5.2. Структура лога (JSON)

Для каждого события формируется стандартизированная запись. Это позволит легко агрегировать данные за любой период:

```json
{
  "id": "1694937949123",           // Уникальный ID (timestamp)
  "date": "2026-09-17",            // Дата для быстрой группировки
  "state": "OVERTIME",             // Какое состояние завершилось (WORK, OVERTIME, REST, REST_VIOLATION)
  "time_start": "10:25:00",        // Время начала фазы
  "time_end": "10:32:15",          // Время окончания фазы
  "duration_seconds": 435          // Длительность в секундах (7 минут 15 секунд)
}

```

#### 5.3. Хранение данных

Поскольку это веб-приложение (PWA), данные лучше всего хранить на клиенте, чтобы не зависеть от сервера и интернета:

* **IndexedDB** — идеальный вариант для хранения массивов таких логов. В отличие от `localStorage`, он не имеет жесткого лимита в 5 МБ и работает асинхронно, не тормозя работу видеокамеры.
* Для упрощения работы с IndexedDB можно использовать легковесные библиотеки вроде `localForage` или `Dexie.js`.

#### 5.4. Предлагаемые графики и метрики для дашборда

На основе собранных логов в приложении можно реализовать раздел «Статистика» со следующими метриками:

1. **Индекс Трудоголизма (Overtime Ratio):** Круговая диаграмма за день — соотношение чистого времени работы (`WORK`) и переработок (`OVERTIME`). Цель пользователя — свести красную зону (овертаймы) к минимуму.
2. **Тренд переработок:** Линейный график по дням/неделям, показывающий среднюю длительность состояния `OVERTIME`. Позволит видеть прогресс (например, «раньше я игнорировал таймер по 15 минут, а на этой неделе ухожу уже через 2 минуты»).
3. **Качество отдыха:** Соотношение успешных сессий `REST` к прерванным `REST_VIOLATION`. Показывает, может ли человек высидеть 5 минут без экрана.
4. **Активность (Heatmap):** График, похожий на историю коммитов в GitHub, показывающий, в какие дни и часы приложение фиксировало наибольшую активность перед экраном.

**Технический бонус:** Такая структура данных позволит в будущем легко добавить экспорт в CSV или JSON, если пользователь захочет проанализировать свои привычки в Excel или передать данные в другие трекеры.
